# PURCHASE-1 · 결정 로그 (DECISIONS)

구매관리(무엇을 샀는지)와 자산관리(누구에게 배정했는지) 두 탭 공동 설계. 두 탭은 데이터를 공유하므로 이 문서와 [`tech/01-data-model.md`](./tech/01-data-model.md)를 기준으로 각자 화면을 만든다. 구매관리는 이 문서 작성자가, 자산관리 화면은 팀원이 맡는다.

## DB는 처음부터 Firestore로 설계한다

QUOTE-1은 PostgreSQL로 먼저 설계하고 나중에 Firestore로 옮겼지만(`specs/QUOTE-1/tech/12-firestore-migration.md`), 이번엔 **처음부터 Firestore 기준으로 설계**하기로 했다. `db/schema.sql`에 있는 PostgreSQL 버전(`asset_products`/`asset_units`/`asset_assignments`)은 **관계·제약조건이 실제로 말이 되는지 로컬에서 검증해본 프로토타입**일 뿐, 배포 기준이 아니다. 구현은 이 문서와 `tech/01-data-model.md`를 정본으로 한다.

이 전환이 의미하는 것(QUOTE-1 마이그레이션 때 확인된 것과 동일, tech/12 §0 참고):
- PostgreSQL 트리거(자동 잠금, 배정 시 상태 자동 갱신)는 Firestore에 없다 → **Firestore 트랜잭션**으로 앱 코드에서 재구현.
- PostgreSQL `UNIQUE` 제약(중복 활성배정 방지)도 없다 → 트랜잭션 안에서 직접 확인 후 써야 함.
- RLS(그룹 권한 DB 강제)도 없다 → QUOTE-1과 동일하게 **서버 코드(`deps.py`류)가 최종 방어선**.

## 확정 사항

| 결정 | 내용 | 이유 |
|---|---|---|
| 상품 마스터 도입 | 상품명을 자유 텍스트 입력이 아니라 미리 정의한 목록(드롭다운)에서만 선택 | "인텔리제이"/"IntelliJ" 같은 표기 차이로 채번·집계가 갈라지는 것 방지. 안 쓰는 상품은 `is_active=false`로만 내리고 삭제 안 함(이미 참조 중인 유닛이 있을 수 있음) |
| 구매관리·자산관리 관심사 분리 | 유닛(자산 유닛: 뭘 언제 얼마에 샀는지)과 배정(누구에게 줬는지)을 별도 컬렉션으로 분리 | 구매관리 탭은 유닛만, 자산관리 탭은 배정만 다룬다 — 한 문서에 다 넣으면 두 탭이 서로의 필드를 침범하게 됨 |
| 고유번호는 유닛 단위 | 구매 시점에 "상품명-순번"(예: 인텔리제이-001) 형태로 유닛마다 하나씩 채번 | 자산관리 탭은 이 번호로만 유닛을 찾음. 두 탭이 번호 체계를 따로 관리하지 않음 |
| 채번은 영구 결번 | 만료·폐기돼도 번호를 재사용하지 않음. 시퀀스는 상품별로 계속 증가만 함 | 이미 발급된 번호가 다른 자산을 가리키게 되는 걸 방지(QUOTE-1 견적번호와 동일 원칙) |
| 만료/폐기 = soft delete | 물리 삭제 없음. 상태를 `EXPIRED`로 바꾸고 처리 시각만 기록, 기본 목록에서는 필터링만 | 구매·배정 이력이 감사 목적으로 남아있어야 함 |
| 만료 시 배정 해제 | **자동으로 하지 않음.** 관리자가 직접 반납 처리 | 라이선스가 만료돼도 갱신 전까지 계속 쓰는 경우가 있어, 시스템이 자동으로 뺏으면 업무에 지장 |
| 배정/반납은 이력이 되는 구조 | "현재 배정 상태"를 한 필드로 덮어쓰지 않고, 배정 1건마다 새 레코드(배정일~반납일)로 쌓음 | 한 유닛이 여러 번 배정·반납·재배정돼도 과거 기록이 안 사라짐. 별도 이력 테이블 불필요 |
| 배정 권한 | **전체관리자만 배정 가능.** 그룹관리자는 자기 그룹 현황 조회만 | QUOTE-1의 승인 권한 구조(전체관리자만 승인)와 동일하게 맞춤 |
| 신청/승인 절차 | 1차 구현에서는 생략. 관리자가 자산관리 화면에서 재고 유닛을 직접 골라 배정 | "필요한 사람이 신청 → 관리자 승인" 흐름은 개인 로그인(USER 역할) 화면이 필요한데, 그건 범위가 커서 이번엔 뒤로 미룸. 나중에 신청 컬렉션만 추가하면 확장 가능(기존 role 구조에 이미 USER가 있어 어렵지 않음) |
| SW/HW/EDU 공통 구조 | 유닛 타입(키/계정)만 SW에 주로 해당하고, 나머지 필드는 자산 유형과 무관하게 동일 테이블/컬렉션 사용 | "모든 자산은 똑같이 관리" — 유형별로 테이블을 쪼개지 않음(QUOTE-1 이전 설계는 SW/HW/EDU를 쪼갰었는데 더 복잡했음) |

## 남은 질문 (구현 중 확정 필요)

1. 상품 마스터 CRUD는 누가 하나(전체관리자만? 그룹관리자도?) — 지금은 구매관리 담당자만 쓸 걸로 가정.
2. 일반 사용자(USER) 로그인 화면 도입 시점 — 신청/승인 흐름을 언제 붙일지는 별도 논의.
3. `asset_products` 문서 ID를 auto-id로 둘지, 사람이 읽기 쉬운 slug로 둘지(`tech/01-data-model.md` §1 참고) — 지금은 auto-id로 잠정 결정(상품명이 바뀔 수 있어서).
