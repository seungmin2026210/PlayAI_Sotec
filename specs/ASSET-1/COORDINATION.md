# ASSET-1 · 구매관리(PURCHASE-1) 담당자와 조율할 사항

> 자산관리 설계(2026-09-28 인터뷰, [`DECISIONS.md`](./DECISIONS.md))가 기존 PURCHASE-1 설계와 부딪히는
> 지점만 모았다. 2026-09-28 자산관리 쪽 제안안대로 **임시 확정**하고 구현했다(아래 각 항목 "합의 결과"). 구매관리 담당자 확인 후 바뀌는 항목만 고친다. 합의 결과는 각 항목의 "합의 결과"
> 칸에 적고, PURCHASE-1 쪽 문서(`specs/PURCHASE-1/DECISIONS.md`, `tech/01-data-model.md`)도 같이 고친다.

## 요약

PURCHASE-1은 "구매 유닛 = 자산"을 전제로 배정까지 구매 유닛에 붙이는 설계였다. 자산관리는
**재판매(대리구매)품이 섞여 있다**는 이유로 자산을 별도 컬렉션(`assets`)으로 분리하고, 구매 유닛은
"골라서 가져오는" 원천으로만 쓴다. 이 때문에 아래 항목들이 바뀐다.

---

## C1. 배정 설계(`asset_assignments`)의 소유권 이동

- **현재(PURCHASE-1)**: `asset_assignments.unit_id` → `asset_units` 참조. 배정 시 `asset_units.status`를
  `AVAILABLE → ASSIGNED`로 갱신(`tech/01-data-model.md` §4, §6, §7 — 설계 스케치, 미구현).
- **제안(ASSET-1)**: 배정은 `assets`에 붙는다. `asset_assignments.asset_no` → `assets` 참조.
  구매 유닛은 배정과 무관.
- **필요한 변경**: PURCHASE-1 `tech/01-data-model.md` §4·§6·§7을 "ASSET-1로 이관" 표시 후 삭제 또는
  링크로 대체. `TECH.md` "남은 작업 2"도 갱신.
- **합의 결과**: _(임시 — 제안안대로 구현)_ 배정은 `assets`에만 붙음. PURCHASE-1 문서 §4·§6·§7 정리는 구매관리 담당자 확인 후

## C2. 구매 유닛 상태 `ASSIGNED`(배정됨) 폐지

- **현재**: `ASSET_UNIT_STATUS_LABELS = 재고 / 배정됨 / 만료`(`backend/app/config.py`), 구매 목록 상태 필터에도 노출.
- **제안**: 구매 유닛에서 "배정됨"은 더 이상 발생하지 않음 → 상태를 `재고(AVAILABLE) / 만료(EXPIRED)`로
  줄이거나, 의미를 바꾸지 말고 그대로 두되 쓰지 않음.
- **대안**: 자산으로 가져온 유닛은 C3의 `asset_link_kind`로 구분하므로 상태값을 건드리지 않는 방법도 있다
  (코드 변경 최소). **자산관리 쪽 추천: 상태값 정리는 구매관리 담당자 판단에 맡김.**
- **참고(용어 혼동 주의)**: 현재 구매 유닛의 `EXPIRED`(라벨 "만료")는 실제로는 **폐기(retire)** 를 뜻한다
  (`routers/asset_units.py: retire_asset_unit`이 `status = EXPIRED` + `retired_at`을 기록). 유효기간 만료와는
  무관하다. 자산관리의 "만료"는 유효기간 종료일 경과 배지(ASSET-1 D21)이므로, 화면에 두 "만료"가 나란히 보이면
  헷갈린다 — 구매 쪽 라벨을 "폐기"로 바꾸는 것을 제안.
- **합의 결과**: _(임시)_ 상태값은 **그대로 두고** 쓰지 않음(코드 변경 없음), 연결 여부는 C3 `asset_link_kind`로 구분. `EXPIRED`→"폐기" 라벨 변경은 구매관리 담당자 판단

## C3. 구매 유닛에 자산 연결 역참조 필드 추가

- **제안**: `asset_units/{unit_no}`에 두 필드 추가. 자산관리 트랜잭션만 채운다.
  - `asset_link_kind: null | "IMPORTED" | "RENEWED"` — 자산으로 가져왔는지(D4·D31), 갱신에 연결됐는지(D32)
  - `asset_nos: string[]` — 연결된 자산번호들(수량 N으로 가져오면 N개)
  - 둘 중 하나라도 있으면 가져오기/갱신 연결 대상에서 빠진다(중복 방지). 가져오기 취소(D35) 시 둘 다 비워진다(C11).
- **구매관리 쪽 영향**:
  - 모델(`models.AssetUnit`)·스키마·presenter에 필드 추가(기본 `null`/`[]`, 기존 문서는 없음 = 비어 있음 취급)
  - 구매 목록/상세 배지: `IMPORTED` → **"자산 등록됨(SW-26-001 외 9건)"**, `RENEWED` → **"갱신에 사용됨(SW-26-001 외 9건)"**
    + 자산 상세 링크
  - 쓰기 주체는 자산관리 트랜잭션뿐 — 구매관리 API로는 수정 불가
- **합의 결과**: _(임시 — 구현됨)_ `models.AssetUnit`·스키마·presenter에 `asset_link_kind`/`asset_link_label`/`asset_nos` 추가, 구매 목록·상세에 배지 + 자산 링크

## C4. 자산으로 가져온 구매 유닛의 폐기

- **질문**: 구매관리에서 유닛을 폐기(`retire`)하면, 이미 가져온 자산은?
- **자산관리 쪽 제안**: 자산은 영향 없음(D2 — 가져오는 시점 복사). 구매 유닛 폐기는 "구매 기록"의 일이고,
  자산 폐기는 자산관리에서 따로. 단, 구매 상세에서 폐기할 때 "자산 SW-26-012 외 9건으로 등록된 유닛입니다"
  (또는 "갱신에 사용된 유닛입니다") 경고 정도는 있으면 좋음.
- **합의 결과**: ~~_(임시 — 구현됨)_ 자산은 영향 없음. 구매 상세 폐기 확인창에 연결 경고 문구 추가~~
  → **변경(D49)**: 가져온 자산 중 살아 있는 것은 함께 폐기(`PURCHASE_RETIRED`), 사용 중 자산이 있으면 구매 폐기 전체 거부.
  갱신 연결 자산은 영향 없음. 구현은 `services/asset_registration.py: retire_unit`(구매관리 `retire_asset_unit`이 호출)

## C5. 구매 유닛의 키 값(`unit_type`/`key_value`) 매핑

- 가져오기 시 매핑 규칙(자산관리 쪽 제안):
  | 구매 유닛 | → 자산 |
  |---|---|
  | `unit_type=KEY`, `key_value` | SW `license_key` |
  | `unit_type=ACCOUNT`, `key_value` | SW/EDU `account_id` |
  | `expire_date` | `valid_to` |
  | `product_name` | `name`(EDU는 `course_title`에도) |
  | `purchased_from` / `purchase_date` | 동일 필드 |
  | `price` | `price` ÷ 수량 N(나머지는 첫 자산 — C9) |
  | `source_quote_id` | `quote_no` |
  | `group_code` | `group_code`(등록 그룹) |
- **확인 필요**: PURCHASE-1 TECH.md "알려진 개선 포인트" — SW인데 유닛 타입 미선택 등록을 막지 않음.
  비어 있으면 자산 쪽에서 빈 값으로 가져와 나중에 입력받으면 되므로 **블로커 아님**.
- **계정 비밀번호**: 구매 유닛엔 비밀번호 칸이 없다. 자산관리에서만 입력·암호화 저장(D15).
  구매 쪽에 비밀번호 칸을 추가하지 **않는 것**을 제안(평문 저장 지점을 늘리지 않기 위해).
- **합의 결과**: _(임시 — 구현됨)_ 위 매핑 그대로(`asset_registration.unit_defaults`). 구매 쪽에 비밀번호 칸 추가 안 함

## C6. `config.py` 상수 공유

- 기존 `ASSET_CATEGORY_LABELS`(SW/HW/EDU)는 그대로 재사용. `EDU` 라벨이 "교육자산"인데 자산관리 메뉴는
  "교육"으로 표기 — 라벨을 바꿀지, 화면에서만 다르게 쓸지.
- 신규 상수(`ASSET_STATUS_*`, `ASSET_SUBCATEGORIES`, `ASSET_NO_*`)는 같은 파일의 PURCHASE-1 섹션 아래
  "자산관리(ASSET-1)" 섹션으로 추가 — 충돌 방지 위해 섹션 분리.
- **합의 결과**: _(임시)_ `ASSET_CATEGORY_LABELS` 그대로, 자산관리 화면만 `ASSET_MENU_CATEGORY_LABELS`("교육"). 신규 상수는 `config.py` "자산관리(ASSET-1)" 섹션

## C9. 수량이 여러 개인 구매의 가져오기 (ASSET-1 D31)

- **배경**: 구매 유닛엔 수량 칸이 없다(`AssetUnitCreate` — 1구매 = 1유닛, `price`는 그 구매의 금액). 그런데
  자산은 "1건 = 사용자 1명"(D5)이라 Copilot 10석 구매는 자산 10건이 돼야 한다.
- **자산관리 쪽 결정**: 가져올 때 **수량 N**을 입력받아 자산 N건을 만들고, 유닛 `price`를 N으로 나눠 각 자산에
  기록(나머지 원 단위는 첫 자산 — P9). 구매관리 쪽 코드 변경은 C3 필드 외엔 없음.
- **확인 필요**:
  - 구매 유닛의 `price`가 **그 구매의 총액**이라는 전제가 맞는지(1석 단가로 입력하는 관행이 있으면 분할하면 안 됨)
  - 실무에서 10석을 유닛 10건으로 따로 등록하는 경우도 있는지 — 있어도 각 유닛을 수량 1로 가져오면 되므로 문제없음
- **합의 결과**: _(임시)_ `price` = 구매 총액 전제로 분할. 단가 입력 관행이면 가져오기 폼에서 금액을 고쳐 넣으면 됨(폼 값 = 총액으로 취급)

## C10. 갱신에 사용된 구매 유닛 (ASSET-1 D32)

- **배경**: 구독 갱신 구매가 구매관리에 새 유닛으로 등록되면, 자산관리에서는 이를 새 자산으로 가져오지 않고
  **기존 자산의 종료일 연장(갱신)에 연결**한다. 새로 가져오면 번호가 바뀌고 자산이 중복되기 때문.
- **구매관리 쪽 영향**: C3의 `asset_link_kind = "RENEWED"` 배지 표시뿐. 갱신 연결은 선택 사항이라 연결 안 된
  갱신 구매 유닛도 있을 수 있다(그건 구매 기록으로만 남음).
- **확인 필요**: 구매관리에서 "이건 갱신 구매"라고 따로 표시하고 싶은지(예: 유닛 등록 시 "갱신" 체크) — 자산관리는
  없어도 동작하므로 **블로커 아님**.
- **합의 결과**: _(임시)_ 구매 쪽 "갱신" 체크는 추가 안 함

## C11. 가져오기 취소 시 구매 유닛 연결 해제 (ASSET-1 D35)

- **배경**: 구매 유닛을 잘못 가져온 경우, 자산관리에서 [가져오기 취소]를 하면 그 유닛에서 만든 자산 N건이 전부
  폐기(사유 "가져오기 취소")되고 유닛의 `asset_link_kind`/`asset_nos`가 **다시 비워진다** — 다시 가져올 수 있게.
- **구매관리 쪽 영향**: 유닛의 "자산 등록됨" 배지가 사라짐. 자산관리 트랜잭션이 C3 필드를 지우는 것뿐이라
  구매관리 코드 변경 없음. 취소 이력은 자산 쪽(`disposed_reason = IMPORT_CANCELLED`)에만 남는다.
- **확인 필요**: 구매 목록에도 "한때 가져왔다 취소됨" 흔적을 남길 필요가 있는지(제안: 불필요).
- **합의 결과**: _(임시)_ 구매 쪽 취소 흔적 남기지 않음
